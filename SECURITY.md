# Security

This is an unofficial client using undocumented Resy endpoints. Account restrictions,
CAPTCHAs, payment challenges, and incompatible upstream responses remain possible.
It is not a supported Resy integration and must not be used to evade access controls.

## Report privately

Use GitHub's private vulnerability reporting feature when available. Otherwise open
an issue asking for a private reporting channel, without exploit details or secrets.
Never attach accounts.json, tasks.json, response bodies, auth tokens, payment IDs,
proxy credentials, opaque reservation URLs, or historical server logs.

## Local safeguards

- macOS/Linux, private local account. JSON and token files are mode 0600; state
  directories are mode 0700. These are not encrypted at rest; backups and processes
  running as your OS user remain part of your trust boundary.
- The server binds only to 127.0.0.1:8000, requires a generated local bearer token,
  rejects browser origins/untrusted Host headers, and does not return validation inputs.
  Do not publish it through a reverse proxy, tunnel, port forwarding, or a public host.
- Submission holds are durable and have no automatic expiry. Never delete state to
  get around an unresolved booking. The local token lives at `.state/.local-server-token`;
  restart both client and server when rotating it.
- Logs and Discord notifications contain summaries, not upstream response bodies.
  Logs generated by older versions may already contain credentials: treat them as
  sensitive, remove shared copies, and invalidate exposed sessions through Resy.
- Run `python scripts/check_secrets.py` against staged files before publishing.
  Enable `.githooks` with `git config core.hooksPath .githooks`.
  This check detects selected patterns and matches local known credentials; it is
  not a proof that arbitrary data or the whole upstream history is secret-free.

## Remaining limitations

The application cannot guarantee inventory or successful checkout. It cannot solve
CAPTCHA or payment/identity verification. Fee parsing is intentionally conservative
and has only synthetic offline coverage in this fork; missing fields stop submission.
An account response may also change, making confirmation unresolved. Holds must stay
in place until the operator verifies the result. HTTP request timeouts bound normal
in-flight waits, but cooperative cancellation is not an operating-system process kill.

Duplicate protection is scoped to a stable account alias/ID plus campaign or venue.
Do not create multiple aliases for the same physical account, rename aliases mid-
campaign, run older clients alongside this version, or independently submit outside
these guards and assume the software can prevent those duplicates.

No production account credentials or live booking tests belong in CI.
